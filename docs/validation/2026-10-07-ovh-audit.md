## What explains the apparent regression

### The seven-to-five decrease removed empty TikTok records

The earlier Harvest job `dc0c47c7665540da96cbf9202e76d537` had seven structured
records: one GHunt record and six SpiderFoot records. Two SpiderFoot records
were representations of the same empty TikTok response: `SOCIAL_MEDIA_PROFILE`
and `RAW_RIR_DATA`. They contained the requested username, null profile details,
`verified=false`, and an empty videos list. They were not evidence of an account.

The current scanner explicitly logs that the TikTok page is not a usable profile
because it is a challenge, missing page, or unrecognized response. Its latest
native event set contains neither empty record. Harvest's capture records
`raw_events=6` and `dropped_empty_profiles=0`: this particular reduction occurred
upstream in SpiderFoot, before Harvest normalization.

The database also contains an older standalone SpiderFoot scan of the same email,
`27F50664`. Replaying its existing events through the current normalizer gives:

| Existing scan | Native events | Usable normalized findings |
| --- | ---: | ---: |
| Standalone `27F50664` | 8 | 4 |
| Earlier Harvest `B096AF1F` | 8 | 4 |
| Latest Harvest `554D6588` | 6 | 4 |

The sets of `(event_type, data, url)` are identical across all three after
excluding empty profiles and the scan's own input. These are three account
candidates and one derived username. This is evidence against an ingestion
regression for this target, not proof of parity on all targets or configurations.

### Standard email investigations do not run Maigret

The latest spec matches the Standard preset: 900 seconds, 100 requests, crawl
enabled, and no pivots. Maigret accepts a username, so the email planner correctly
does not pass the email to it. SpiderFoot did produce a username that
`pivot_candidates()` accepts, but `Engine.pivot()` returns immediately when
`limits.pivots=0`.

This is a material coverage limitation of the current workflow. A prior Harvest
Maigret run for the same derived handle, capture 511 / job
`c9970898a70a4beba7fa13e8e012e01d`, retained two records with `top_sites=500`.
Those records are not necessarily additional unique accounts; they establish that
the tool can run for this handle and was omitted from the latest job.

Deep enables up to three one-hop pivots. However, **Maigret pivot jobs always use
500 sites**, even under Deep (`engine.py`, `PIVOT_TOP_SITES`). Only a directly
requested Deep username scan selects all sites. Switching the email job to Deep
therefore still does not provide an all-sites Maigret sweep of the discovered handle.

### Maigret breadth changes explain large count differences

For another single historical username, captures 458, 460, 462, and 463 each
retained 26 records with all sites selected; captures 512 and 538 each retained
eight with `top_sites=500`. These are historical comparisons, not simultaneous
controlled trials, so the entire difference cannot be attributed to the cap alone.
The changed scan breadth is nevertheless explicit in the saved task payloads.

Installed Maigret is 0.6.6. Its bundled database has 5,897 definitions, 694 marked
disabled; actual eligible checks also depend on Maigret's selection rules. The
capability text describing a full sweep as approximately 500 sites is inaccurate
for this image. Quick selects 100, Standard selects 500, and direct Deep username
scans select all sites. The wrapper also pins the database with `--no-autoupdate`,
uses one retry, 30-second site timeouts, and 32 concurrent checks at the deployed
128-connection/two-worker-thread settings. Standalone comparisons must match these.

## Confirmed failures and production gaps

Bing supplied 30/32 results; none of the 32 passed identifier relevance checks. Establish a working search provider through the required egress path and measure relevant-source coverage, not just HTTP 200. |
| P1 | Tool success does not establish check coverage | SpiderFoot completed despite proxy 502s for two sites, TLS failures for two others, a redirect loop, and an unusable TikTok page. Preserve per-module/per-site attempted, succeeded, absent, blocked, errored, and unsupported counts. A terminal scan state alone cannot distinguish absent evidence from failed acquisition. |

The exact persistence/read-path cause remains unisolated. GHunt/Maigret callers ignore the subprocess stdout/stderr returned by `_exec`; temporary reports are removed after normalized capture creation. Persist bounded, credential-redacted diagnostic summaries and original tool artifacts with appropriate access controls; do not dump raw stderr, which can contain credentials. |
| P1 | Coverage choices are easy to misunderstand | Email Standard omits username enrichment; Deep pivots still cap Maigret at 500. Disable unsupported integrations through honored settings/code guards, or provision and validate them. These failures did not remove the four persisted scan findings. |
| P2 | Some HTTPS checks skip verification | Numerous `InsecureRequestWarning` entries occur during account checks. Trace the call-site overrides and use verification by default, with explicit handling for unsupported sites. Blanket TLS relaxation is not a coverage fix. |

## Prioritized implementation and acceptance

1. **Make coverage measurable.** Persist safe tool diagnostics, effective arguments,
   versions/database hashes, and per-check outcomes; repair scan-log availability.
   Acceptance: a deliberately failed check is distinguishable from a completed
   negative check in the saved job, and survives container recreation.
2. **Make the preset's scope explicit.** Include the email-to-username path and
   configurable pivot breadth in a full-coverage preset, retaining candidate
   attribution and shared budgets. Correct the approximately-500-site claim.
   Acceptance: the plan and actual executions agree, and a full-coverage email
   job runs the configured Maigret breadth on an eligible discovered handle.
3. **Restore and measure acquisition.** Validate search engines through the actual
   proxy, handle provider rate limits, and expose blocked/unsupported tool
   sub-checks. Acceptance: authorized test queries find known relevant sources;
   provider outages never masquerade as proof that no sources exist.
4. **Gate releases on parity.** Use saved native outputs for deterministic adapter
   tests and matched live runs for acquisition. Match target, version, credentials,
   site database, modules, egress, concurrency, retries, timeout, and crawl policy.
   Compare usable unique findings and field retention, with a reason for every
   exclusion. Cover the actual SpiderFoot `{events, total}` response contract,
   not just the mocked paginated form.
5. **Finish deployment hygiene.** Disable unused optional integrations, address TLS
   and module warnings, verify restart/network reattachment, and separately prove
   backup restoration and monitoring. The current audit did not validate disaster
   recovery, sustained multi-job load, or external alerting.

Increasing result counts by restoring empty TikTok records, accepting unrelated
search results, or presenting username coincidences as confirmed ownership would
invalidate the evidence rather than repair coverage.
